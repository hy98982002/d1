## 二、为什么你这次判断是对的（逐条对齐你的体系）

### 1️⃣ 从「体系结构」看 —— RBAC 不匹配

你现在的核心事实是：

* **三级内容体系**：Beginner / Intermediate / Advanced
* **权限本质**：
  👉 *“这个用户能不能看这门课”*
* **不是**：
  👉 *“这个角色能不能对某个资源执行某种操作”*

RBAC 解决的是：

> **Who (Role) → can do What (Action) → on Which Resource**

而你当前的问题是：

> **User → 是否满足课程的 access 条件**

这两者**不是同一类问题**。

---

### 2️⃣ 从「宪法（CLAUDE.md）」看 —— RBAC 是违背设计哲学的

你在 CLAUDE.md 里反复强调的几条原则（我直接翻译成工程语言）：

* ❗ **避免把业务语义编码成 UI 或抽象结构**
* ❗ **显式优于隐式**
* ❗ **避免为未来假设付出现在的复杂度**

RBAC 的典型副作用正好相反：

* 把**业务规则**塞进 `role → permission → mapping`
* 引入：

  * role 表
  * permission 表
  * role_permission 表
* 最终出现：

  > “这个人明明是会员，为什么还访问不了？”

👉 **RBAC 会让你“用权限系统掩盖真实业务规则”**
这和你现在的设计理念是**硬冲突**。

---

### 3️⃣ 从「商业模型」看 —— 你不是“角色驱动型产品”

你现在的商业模型是：

* 免费 / 单买 / 会员
* 折扣 / 访问 / 试看

这在本质上是：

> **商品属性 + 用户状态 = 是否允许访问**

而不是：

> **角色集合 = 权限集合**

所以你在评测中写的这句话是**关键正确点**：

> *“核心是内容访问控制，而非操作权限控制”*

这是整个判断的**分水岭**。

## 三、你给出的「替代方案」是否正确？

### ✔ 结论：正确，而且是当前最优解

你给的示例：

```ts
export const canAccessCourse = (user: User, course: Course) => {
  if (course.level === 'beginner') return true
  if (user.isMember && course.level === 'intermediate') return true
  if (user.purchasedCourses.includes(course.id)) return true
  return false
}
```

这在工程上有三个**巨大优点**：

1. **业务语义显式**
2. **可测试**
3. **未来可平滑演进**

比 RBAC 强 10 倍。
